# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

PixieVeil is a DICOM anonymization server: it receives medical images via DICOM C-STORE, anonymizes them (profile-based), optionally defaces head scans with nnU-Net, organizes them into a numbered study/series hierarchy, and holds completed studies ready for export to a remote DICOM node or HTTP endpoint. A web dashboard exposes live metrics and is also where a user manually triggers each study's export — nothing is sent automatically.

## Commands

```bash
# Bootstrap: .python venv (python3.12) + pip install -e . + install.py
./install

# Run the server directly
python pixieveil.py

# Or via the control script (foreground; writes/checks a pidfile)
./pixieveil.sh start    # also: stop, restart, status

# Interactive setup (installs torch/nnunetv2, downloads nnUNet model) —
# normally run automatically by ./install, but can be re-run standalone
python install.py

# Download defacing model only
python install.py --download-model

# Install core dependencies without the ./install wrapper
pip install -e .

# Install the deface extra (simpleitk/nibabel/numpy/gdown/nnunetv2) — still
# needs install.py afterwards for a CUDA-matched torch build
pip install -e ".[deface]"

# Dashboard users (no web sign-up): add/passwd/list/disable/enable/delete/
# admin/logout/token-add/token-list/token-revoke
python -m pixieveil.auth add alice --admin

# Install test dependencies (pytest) and run the suite
pip install -e ".[test]"
pytest
```

See [INSTALL.md](INSTALL.md) for the full bootstrap/systemd/OpenRC flow.

## Architecture

```
Modality ──C-STORE──► DicomServer (pynetdicom)
                           │
                      CStoreSCPHandler
                           │
                      StorageManager.process_image()
                        ├─ SeriesFilter.should_filter()
                        ├─ Anonymizer.anonymize()
                        └─ StudyManager.add_image_to_study()
                           │
                  (asyncio.create_task per study)
                  StorageManager._process_study()
                        ├─ ExamExtractor.extract()        [asyncio.to_thread] → <NNNN>.exam.json
                        └─ Defacer.deface_series()        [asyncio.to_thread]
                           │  (study now "ready" — sits in base_path)
                           ▼
                  /studies dashboard → user clicks Send/Upload/RHYTHM
                  StorageManager.manual_send_dicom() / manual_upload_http()
                        ├─ DicomStorage.send_study()      [asyncio.to_thread]
                        └─ ZipManager → RemoteStorage     [asyncio.to_thread]
                  StorageManager.manual_upload_rhythm()   (returns once queued)
                        └─ ZipManager → RhythmStorage.upload_study()
                  StorageManager.reconcile_rhythm_jobs()  (completion loop)
                        └─ RhythmStorage.check_job() → on COMPLETE: retain/delete + archive
```

Single asyncio event loop. All blocking I/O (nnUNet inference, ZIP, file I/O) uses `asyncio.to_thread`. GPU jobs are serialized via a class-level `threading.Semaphore(1)` on `Defacer`.

## Key design decisions

**Sidecar files** — Each study has `<study_number>.state.json` written atomically (write-to-tmp + rename). Tracks `status` (`receiving → complete → defacing → ready → archived`, with `defacing_failed` / `defacing_disabled` as side branches — see below), `archived_via` (`"dicom"` / `"http"` / `"rhythm"` / `null`), the `rhythm_*` upload-job fields (see RHYTHM export below), `exported_at` / `purged_at` (retention, see Post-export retention), and per-series defacing progress. On restart, `StudyManager.initialize_from_sidecars()` re-queues any study that did not finish reaching `ready` (i.e. still `complete`, `defacing`, `defacing_failed`, or `defacing_disabled`); studies already `ready` or `archived` are left alone. `StudySidecar.load_all()` first calls `migrate_legacy_sidecar_names()`, which renames pre-rename `<NNNN>.json` → `<NNNN>.state.json` and `<NNNN>_exam.json` → `<NNNN>.exam.json` in place (idempotent) — so an upgrade needs no manual migration and the `????.state.json` glob keeps exam sidecars out.

**Proactive export artifacts** — `export_path/<NNNN>.zip` + `<NNNN>.json` are built as soon as a study is *export-ready*: `status == ready` (anonymized + defaced), a resolvable `protocol_id` (protocol picked + real UUID), `image_quality` set, at least one CT series, **and** actually anonymized under the `rhythm` profile. The last check lives in `_rhythm_manifest_item_sync()` (so it surfaces everywhere a manifest item is built — the dashboard manifest preview's `blockers`, `manual_upload_rhythm`'s refusal, and artifact prep — not silently): `_rhythm_anonymized_sync()` reads the first CT slice of each series and returns a blocker if any tag that profile strips (`DeviceSerialNumber` / `StationName` / `Manufacturer` / `ProtocolName`) still carries a value. A study received before the profile was switched must be re-received under `rhythm`, not re-exported. `_prepare_export_artifacts_sync()` runs at the end of `_process_study()` (usually a no-op — blockers still unfilled), after every `save_exam()` (an edit may have cleared the last blocker or changed a value baked into the DICOM), and each completion-loop tick via `prepare_ready_exports()` (self-healing: covers studies made `ready` before this existed). It rebuilds only when the study dir or exam sidecar is newer than the artifacts (`_export_artifacts_current_sync`), and deletes the pair if the study stops qualifying. `site_code` is **not** a data blocker here — it's a destination-config value — but the written manifest is a complete, shippable v2 document: real `batch` (`_new_rhythm_batch_id()`) and the configured `site_code` (left `null`, not `"SITE"`, when RHYTHM is unconfigured, so a bad manifest fails loudly). Partner tooling watching `data/export/` can submit `<NNNN>.json` as-is; `manual_upload_*` still rewrites `batch`/`site_code` when the operator sends from the dashboard. So `data/export/` fills up on its own without RHYTHM/HTTP being configured or any button click. **Out-of-band export write-back** — tooling that shipped the ZIP itself then calls `POST /api/studies/{n}/actions/mark_exported` (optional body `{"via": "rhythm"|"http"|"dicom", "sha256": "<hex>"}`, default `via="rhythm"`; `sha256` mismatch vs the prepared manifest is a non-fatal `warning`). `StorageManager.mark_exported()` runs the same bookkeeping a successful `manual_*` would — `mark_study_archived(via)` + `_finish_export_sync` (stamp `exported_at`, clear deface scratch, purge now if `retain_after_export_days` is unset) — so the study leaves `ready`, stops being re-prepared each tick, and its retention clock starts. Without this call an externally-shipped study stays `ready` forever and its `data/dicom/<NNNN>` dir + `data/export/<NNNN>.zip` are never reclaimed.

**Manual-only export** — `StorageManager._process_study()` never sends a study anywhere: once exam extraction and defacing finish, the study is marked `ready` and sits in `base_path`. Export only happens when a user clicks Send/Upload on the `/studies` dashboard, which calls `StorageManager.manual_send_dicom()` / `manual_upload_http()` / `manual_upload_rhythm()`. The first successful export marks the study `archived` and stamps `exported_at` (`_finish_export_sync` — DICOM takes priority if the user sends via both). The study **directory stays in `base_path`** after export; nothing is moved. If `storage.retain_after_export_days` is not set, `_finish_export_sync` purges the directory + `export_path/<NNNN>.{zip,json}` pair + deface scratch right then (and stamps `purged_at`); otherwise `enforce_retention_purge()` does it once the window elapses. `resolve_study_dir()` therefore only ever checks `base_path` — a re-send works for as long as the directory is still there, and returns "study directory not found" once it's been purged (re-receive the source DICOM to send again).

**Defacing failure blocks export, not just logs it** — After `_deface_study()` finishes, `_process_study()` checks `StudySidecar.has_undefaced_head_series()` (any series flagged `is_head=True` with `defaced=False`) before deciding what status to mark. If any head-scan series failed to deface, the study is marked `defacing_failed` instead of `ready`, and `manual_send_dicom`/`manual_upload_http` both refuse to export a study in that state — otherwise it would sit in the dashboard looking identical to a fully-defaced `ready` study, and an operator could export it with a patient's face still in the pixel data. `defacing_failed` is included in the crash-recovery requeue set (alongside `complete`/`defacing`), so a restart retries just the series that still need it — `is_series_defaced` already makes re-running defacing idempotent for series that succeeded the first time, so this reuses the existing recovery path instead of needing a separate "redo defacing" action.

**Defacing disabled is flagged, not silent** — With `defacing.enabled: false`, `_process_study()` still runs `_deface_study(..., classify_only=True)` so head/topogram classification lands in the sidecar. A study with a head-scan series is then marked `defacing_disabled` (not `ready`, and distinct from `defacing_failed`, which means defacing was on but didn't complete). Export is refused the same way (`StorageManager._deface_export_block`), and the status is in the requeue set, so enabling defacing and restarting defaces those studies.

**RHYTHM exam extraction** — On every completed study, `ExamExtractor.extract()` reads the anonymized DICOM headers under `study_dir` and writes `<study_number>.exam.json` (JSON, not YAML — machine-written/machine-read, mirrors `StudySidecar`'s format) with whatever RHYTHM Manual-Exam-Entry fields are derivable (contrast, patient age, CTDIvol, scanner make/model, indication/protocol-type/exam-group when the study matches a scanner and protocol in the protocol catalog — see "Protocol catalog" below). **Terminology**: the sidecar's `series` list is keyed by DICOM `SeriesNumber` — it is *not* the same thing as an irradiation event. One RDSR acquisition (one real dose event) can be reconstructed into several DICOM series at different kernel/thickness, so several `series[]` entries legitimately share one event; `rdsr.acquisitions[]` is the authoritative per-irradiation-event record. Every CT-modality series — including topograms/localizers — gets a `series[]` entry flagged `is_topogram`; a topogram is a real irradiation event and stays in the dose record rather than being dropped. Only genuinely non-CT objects riding along in the study directory (e.g. a rendered Dose Report screen capture) are excluded. Each `series[]` entry also carries per-series technique parameters read straight off the image headers — `slice_thickness_mm`, `exposure_time_ms`, `convolution_kernel`, `patient_position`, `single_collimation_width_mm`, `total_collimation_width_mm`, `spiral_pitch_factor` — and a best-effort `dlp_mgy_cm` estimated as CTDIvol × the z-extent spanned by `ImagePositionPatient` across the series (skipped for topograms, where that relationship doesn't hold); `notes` flags it as an estimate and says to prefer `rdsr.acquisitions[*].dlp_mgy_cm` when an RDSR is present. Fields it still cannot determine (image quality, unmatched indications/scanners) are left `null` with an explanation in `notes`. (These extracted indication/scanner/bucket fields feed the `/studies` dashboard display and the sidecar's own `protocol_type`/`examination_group` recompute — they no longer feed the RHYTHM manifest, which since submodule `f4120f5` carries only a `protocol_id` from which RHYTHM derives all of that; see "RHYTHM export" below.) **Pre-anonymization hints** — `Manufacturer` / `ManufacturerModelName` / `ProtocolName` / `StudyDescription` / `SeriesDescription` are exactly the fields the `rhythm` profile strips, so by the time extraction runs on the completed study they're gone and every protocol-catalog match would miss. `StorageManager.process_image()` captures those five from each *raw* image before `anonymize()`, accumulates them per study (first non-empty wins), and flushes to `<study_dir>/.exam_hints.json` once per series; `_write_exam_sidecar` / `_manual_reextract_sync` pass them to `ExamExtractor.extract(hints=…)`, which uses them only where the (now blank) header has nothing — a real header value always wins. The file is written under every profile (cheap, harmless) and `ZipManager` unconditionally excludes it from export archives (it holds the very values `rhythm` removes). `BodyPartExamined` / `ContrastBolusAgent` / technique tags / RDSR content are *not* in `rhythm`'s `RemoveTags`, so they need no hint. Runs first in `_process_study()` — before defacing, not just before export — since it only needs anonymized headers (defacing rewrites `PixelData` only, never metadata); this way the sidecar survives a defacing crash and isn't blocked behind CPU-mode nnU-Net inference. Skipped if the sidecar already exists, so a re-queued retry never overwrites paper-note data merged in later.

**RDSR content parsing** — Confirmed on our Siemens Emotion 16: its "Dose Report" object is `SOPClassUID`-wise a Secondary Capture image (a rendered screenshot), but the same object also carries the full X-Ray Radiation Dose Report structured-content tree (TID 10011/10013) that a native RDSR would — Siemens converts SR→SC for compatibility but keeps the content sequence attached (`DerivationDescription: "Convert syngo SR to DICOM SC"`). `ExamExtractor._parse_rdsr_content()` walks that tree by DCM concept code (works on a native RDSR too, not just this vendor quirk) and populates the sidecar's `rdsr` key: `total_dlp_mgy_cm` plus, per acquisition, `pitch`, `kvp`, `mean_ma`/`max_ma`, `rotation_time_s`, `mean_ctdivol_mgy`, `dlp_mgy_cm`, `acquisition_type`, `modulation_type`. This is why the DICOM SCP (`pixieveil/dicom_server/server.py`) also registers `XRayRadiationDoseSRStorage` now — without that presentation context a *native* RDSR would be refused at C-STORE association negotiation even though this vendor's SC-hybrid already got through on the pre-existing `SecondaryCaptureImageStorage` context. Always prefer `rdsr.acquisitions[*].mean_ctdivol_mgy` over `series[*].ctdi_vol_mgy` when both are present. How the per-image `CTDIvol` tag relates to the RDSR is decided per study from the data (`_classify_per_image_ctdivol` → `rdsr.per_image_ctdivol`: `per_acquisition` / `cumulative` / `unclear`), not assumed per scanner. An earlier note claimed the Emotion 16 reports cumulative dose-to-date; real studies contradict that. On the Emotion 16 and the SOMATOM go.All/go.Now alike it is per-acquisition, reading up to ~16% above the RDSR mean because `series[*].ctdi_vol_mgy` is the max over a tube-current-modulated series' images.

**Post-export retention** — `storage.retain_after_export_days` (optional) keeps an exported study on disk for N days *after* export instead of deleting immediately. Off by default (immediate purge in `_finish_export_sync`, prior behaviour). Switching it off later (live from `/settings` or across a restart) makes the next `enforce_retention_purge_sync()` pass purge every already-exported, unpurged study — off means "delete immediately" for those too; a study with no `exported_at` is still kept. The retention clock is `StudySidecar.exported_at`, stamped on first successful export — for RHYTHM, when the ingest job reaches `COMPLETE` (`_finalize_rhythm_export`), so a study uploaded but never confirmed keeps its `export_path/<NNNN>.zip` **indefinitely** as the retry source. `StorageManager.enforce_retention_purge_sync()` runs alongside quota enforcement in the completion loop: it walks the in-memory sidecars (`StudyManager.all_sidecars()` — every sidecar write goes through `StudyManager`, so the loop never re-reads `????.state.json`), and for each `archived` study whose `exported_at` is older than the window it calls `_purge_study_artifacts_sync()` — `rmtree` the study directory, delete `export_path/<NNNN>.{zip,json}`, `_clear_deface_temp_sync()` the `pixieveil_deface_<NNNN>_*` scratch — then stamps `purged_at`. **The `<NNNN>.state.json` and `<NNNN>.exam.json` records are kept permanently** (they act as the audit database); only the bulky artifacts go. There is no separate retention directory any more — exported studies sit in `base_path` and **do** count toward `max_storage_gb`, so `enforce_storage_quota_sync()` can purge an archived study (via the same `_purge_study_artifacts_sync` + `purged_at`) before its window elapses if disk pressure demands it. `export_path` (default `<base_path>/../export`, key `storage.export_path`) holds the `<NNNN>.zip` + `<NNNN>.json` pair that HTTP and RHYTHM exports write *before* sending (see RHYTHM export); DICOM C-STORE produces no artifact there.

**`rhythm` anonymization profile** — A third profile alongside `research`/`gdpr`, required for RHYTHM export. RHYTHM re-validates every uploaded slice against its own `GDPR-strict.json` (vendored at `reference/uploader/ct_upload_platform/GDPR-strict.json`) and rejects the studyset if any tag it marks "must be removed" still carries a value — the `research`/`gdpr` profiles fail this because they *replace* dates with a placeholder instead of removing them, don't touch device-identity tags (`Manufacturer`, `StationName`, `DeviceSerialNumber`, …), and leave a pseudo `PatientID` (`reference/anon_rhythm.json` is a captured 49-file rejection). The `rhythm` profile adds `RemoveTags` — a list of DICOM keywords `Anonymizer.strip_tags()` deletes outright as the final `anonymize()` pass (so it wins over `anonymize_dates()`'s substitution). The list is exactly the pydicom-resolvable `null`-directive keywords from RHYTHM's `GDPR-strict.json` (the display-name-only entries the validator can't address by `hasattr` are skipped), plus `PatientName`/`PatientID`; `tests/test_anonymizer_rhythm.py` cross-checks it against the vendored file (fails on a `git submodule update --remote` that adds a tag) and round-trips a synthetic CT carrying the real rejected tags. `PatientAge`/`PatientWeight`/`PatientSize` are `KEEP` (GDPR-strict marks them so; the manifest uses age/weight). `PatientID` uses `PSEUDO` (kept for the anontrail) then `RemoveTags` deletes it from every shipped file — RHYTHM keys studies on its own Repository Study ID. `Anonymizer.remove_overlays()` was also widened to the full 60xx/50xx repeating-group ranges + waveform/audio groups (a strict anonymization improvement, applied to all profiles).

**RHYTHM export (third manual path)** — Alongside DICOM C-STORE and HTTP ZIP, a study can be pushed to the RHYTHM CT upload platform via its v2 "server-assigned batch" API. There is no manifest-ingest endpoint on RHYTHM's side: its partner tooling fans out one resumable chunked upload per studyset, tagging each with a shared `batch` string and a `manifest_item` dict. `pixieveil/processing/rhythm_manifest.py` builds that item from the *effective* exam sidecar (canonical values already carry the manual overlay); `RhythmStorage.upload_study()` (`rhythm_storage.py`) drives `chunked/init → per-chunk POST (sha256, retried) → complete/` and **returns once the ingest job is queued — not once it passed**. **`protocol_id`, not coded fields** — RHYTHM v2 (submodule `f4120f5`+) dropped the per-item `clinical_indication_code`/`anatomical_region`/`contrast_code`/`patient_group_code`/`scanner_id`/`protocol_name`; an item now names one `protocol_id`, the UUID of a `CTProtocol` registered on RHYTHM's Protocol Records page, and the server derives region/indication/contrast/protocol type/exam group/scanner from it. PixieVeil resolves that UUID through the protocol catalog (`protocol_catalog.ProtocolCatalog`, loaded by `RhythmStorage` and shared as `StorageManager.protocol_catalog`) from the exam sidecar's `rhythm.protocol_key` — filled automatically when the study matched a catalog protocol, or picked by the operator on `/studies` (a manual-overlay field). A key set but absent from a populated catalog is a hard error; an unset key leaves `protocol_id` null → a blocker. A protocol whose `rhythm_uuid` is null (or the all-zeros `NIL_UUID`) **still loads** (offered in the dropdown as "(UUID pending)") but `uuid_for()` resolves it to `null`, so the study stays blocked rather than uploading a bogus `protocol_id`. Refusals point the operator to `/protocols`, whose Unmatched inbox replaced the old auto-appended placeholder stubs. `item["site_code"]` still comes from `settings…rhythm.site_code` (authoritative) and must match the registered protocol's own `site_code` case-insensitively or RHYTHM fails the job — if the catalog carries a top-level `site_code` that disagrees with settings, it fails validation (RHYTHM export is disabled at startup, and `/protocols` refuses to save it) rather than let that reach RHYTHM. The old code tables and their ported constants are gone from `rhythm_manifest.py`; the `integrations/rhythm/*_protocol.yaml` reference files stay — they're the human-facing definition of what to register upstream, and you record each registered protocol's UUID on `/protocols`. `StorageManager.manual_upload_rhythm()` / `manual_upload_rhythm_batch()` (one `batch` id per dashboard action) refuse a study when: RHYTHM isn't configured, the anonymization profile isn't `rhythm` (only that profile strips every tag RHYTHM's `GDPR-strict` ingest validator requires absent — `research`/`gdpr` both leave dates, device identity, descriptions and a pseudo `PatientID` that the validator rejects; proof is `reference/anon_rhythm.json`, a real 49-file rejection captured under `research`. This gate reads the *current* `settings.anonymization.profile`, not what each study was actually anonymized with, so a study received under another profile then switched to `rhythm` passes the gate but is rejected by RHYTHM at ingest; anonymization is one-shot at receive time and only the anonymized copy is kept, so the fix is to re-send the source DICOM under `rhythm`, not re-export), the study is `defacing_failed`, a RHYTHM-required manifest field is still unset (notably `image_quality` — left null by extraction, filled on `/studies`), or the study holds no CT image series. The export ZIP is built — with a `ZipManager` `exclude` predicate that keeps only CT / Enhanced CT / Legacy Converted Enhanced CT SOP classes (the rendered Dose Report Secondary Capture and any native RDSR are dropped; an unreadable series fails safe, excluded) — straight into `export_path/<NNNN>.zip`, **before** the upload. Its `sha256`/`size_bytes` are then computed and set on the manifest item (RHYTHM verifies the checksum before extracting), and `_write_rhythm_export_manifest_sync()` writes the v2 batch manifest carrying those real values + the `batch` to `export_path/<NNNN>.json`. That pair is the audit copy / retry source: it persists on a failed or never-`COMPLETE` job (a later attempt overwrites it) and is aged off together with the study directory once retention elapses. `manual_upload_rhythm` persists `rhythm_batch`/`rhythm_session_id`/`rhythm_job_id`/`rhythm_job_status_url`/`rhythm_status` plus `rhythm_zip_sha256`/`rhythm_zip_size` on the study sidecar (via `StudyManager.set_rhythm_job()`) and returns; `StorageManager.reconcile_rhythm_jobs()` runs each completion-loop tick, polls every in-flight job with `RhythmStorage.check_job()`, and on a terminal `COMPLETE` runs `_finalize_rhythm_export` → `mark_study_archived(via="rhythm")` + `_finish_export_sync` (stamp `exported_at`, clear deface scratch, and purge now if retention is off) + counters. `PARTIAL`/`FAILED` just record the state — the study stays `ready` so the operator can retry. `archived_via` gains `"rhythm"` as a fourth value. For manual testing against RHYTHM's own validator, `StorageManager.build_rhythm_manifest_preview_sync()` builds the batch manifest **itself** (top-level `type`/`items`, so RHYTHM detects it as v2) without uploading — no `sha256`/`size_bytes`, `site_code` left null and flagged rather than back-filled, and an extra top-level `blockers` key (allowed by v2's `additionalProperties: true`) listing anything that would stop a real upload. The dashboard exposes it at `GET /api/studies[/{n}]/rhythm-manifest` (`?studies=1,2,3`; `&download=1` returns a pristine `rhythm_manifest.json` with `blockers` stripped) plus per-study "preview / download" links — **the manifest is only ever built in the Python backend** (`rhythm_manifest.build_*`); the `/studies` page just links to those endpoints, it never assembles one client-side. For a single already-exported study the endpoint serves `export_path/<NNNN>.json` verbatim (`load_export_manifest_sync`) — the real manifest with checksums and the batch it actually went up under — instead of minting a fresh checksum-less preview.

**Patient ↔ RHYTHM correspondence (erasure requests)** — RHYTHM keys its `StudyMapping` on our *anonymized* StudyInstanceUID unchanged, and its own ID for the study is the Repository Study ID (`Patient.pseudo_id` == `CTExamination.repository_study_id`), which the job-status reply does not carry. So when `reconcile_rhythm_jobs` sees `COMPLETE` it calls `RhythmStorage.fetch_study_ids(anonymized_study_uid)` (`GET /api/v1/studies/<uid>/` → `patient_pseudo_id` / `orthanc_study_id`) via `_record_rhythm_study_ids` and stores `rhythm_repository_study_id` / `rhythm_orthanc_study_id` on the sidecar. Archiving does not wait for it; a failed lookup is backfilled on later ticks (COMPLETE + no id), at most once per `RHYTHM_ID_RETRY_S`. `StudyManager.set_rhythm_job` also keeps `rhythm_uploads[]`, one entry per attempt (a call carrying `batch` starts a new one; later calls update the last; a pre-history sidecar is seeded from its `rhythm_*` fields), so a retry no longer overwrites the earlier job ids. `pixieveil/storage/correspondence.py` builds the patient → study → RHYTHM table from the permanent `.state.json` sidecars only (works after purge): exact, case-insensitive match on original/pseudonymized PatientID or StudyUID, study number, Repository Study ID, job id, batch, session id. Exposed as the admin-only `/lookup` page + `GET /api/lookup?q=` / `?all=1&format=csv` (each call logged as `Audit: user=… action=lookup`) and `python -m pixieveil.storage.correspondence <id> | --all [--csv]`. Output holds original PatientIDs — same sensitivity as the anontrail.

**Manual provenance overlay** — `ExamSidecar`'s data carries a top-level `manual` key (`{"edited_at": ..., "fields": {"patient.weight_kg": 34.0, ...}}`) recording which dotted paths a human set via the `/studies` dashboard page, distinct from the canonical (effective) values those paths already hold. This exists because `_process_study()` skips extraction entirely when `<study_number>.exam.json` already exists — a naive re-extraction would otherwise silently discard hand-entered fields (weight, image quality, an indication the lookup table couldn't match, per-series DLP/CTDIvol read off a console screen). `pixieveil/processing/exam_merge.py` is the single place this overlay logic lives: `apply_manual()` writes `manual.fields` into the canonical dict (per-series fields keyed `series.<series_number>.<leaf>`, never list index, since `extract()` rebuilds `series[]` from disk and the set can change between runs), `merge_extracted()` re-applies a previous sidecar's `manual` block onto a freshly extracted one, and `recompute_buckets()` reruns `exam_extractor._determine_bucket()` (a module-level function, not a method — it needs no lookup-table state) so a manually-entered weight or age immediately updates `protocol_type`/`examination_group` instead of leaving them stale. Both the PUT-exam handler (`StorageManager.save_exam`) and the manual re-extract action (`StorageManager.manual_reextract`) go through this module so the semantics never drift between the two call sites.

**Patient weight/age write-back** — `StorageManager._save_exam_sync()` also patches a manually-corrected `patient.weight_kg`/`patient.age_years` straight into `PatientWeight`/`PatientAge` on every anonymized `.dcm` file under the study's directory (`_writeback_patient_fields_sync`), not just the exam sidecar — otherwise the correction would never reach whatever gets exported. Only the field(s) present in *this* save's `manual_fields` are patched (not the full merged overlay), and only while the study is still sitting in `base_path` (`sidecar.status != "archived"`); once a study is archived its DICOM copies are already gone, so nothing to patch. Other manual fields (indication, protocol name, per-series DLP, etc.) stay sidecar-only — they don't have a clean 1:1 DICOM tag to write back to.

**Exam completeness** — `exam_merge.REQUIRED_PATHS` (image quality, weight, age, region + clinical indication, IV contrast, RHYTHM protocol — `rhythm.protocol_key`, which replaced the scanner ID since RHYTHM v2 derives the scanner from the protocol) defines when an exam record is complete — except weight, which `required_paths()` drops for head/mastoid exams (`is_weight_optional`, mirroring RHYTHM's own rule); `missing_required()` is exposed per study as `missing_fields`/`completeness` in `/api/studies` and the detail endpoint. Advisory only: the `/studies` page flags incomplete exams, warns before exporting one, and its bulk export skips them unless explicitly included — the server never refuses an export for missing exam data (unlike `defacing_failed`).

**Shutdown stops defacing** — nnU-Net inference runs in a child process (`python -m pixieveil.processing.nnunet_worker`, its own process group via `start_new_session`, output in `<scratch>/nnunet_worker.log`), not in the `asyncio.to_thread` worker: a thread can't be interrupted, so Ctrl-C used to wait for CPU inference to finish. `StorageManager.stop()` calls `Defacer.cancel_all()` (class-level `_cancel` event + tracked `_procs`): SIGTERM to each worker's process group (nnU-Net's own pool included), SIGKILL after `CANCEL_GRACE_S`. The defacing thread then raises `DefacingCancelled` (also checked before each series); `deface_series` re-raises it without touching the series, and `_process_study` logs it at INFO and leaves the study in `defacing`, which the restart re-queue picks up (already-defaced series are skipped). `StorageManager.start()` calls `Defacer.reset_cancel()`; conftest resets it around every test.

**Device fallback** — `Defacer._resolve_device()` validates `cuda`/`mps`/`cpu` at startup with a test tensor and falls back to CPU automatically.

**Live updates (SSE)** — `GET /api/events` streams *thin notifications, never data*: `study {n,status}` (fired by `StudyManager._save()` via its `on_change` hook, so every sidecar write — status, series, RHYTHM job — is covered in one place), `exam {n}`, `progress {n,kind,done,total}` (kinds `receive`/`deface`/`dicom`/`rhythm`, from `process_image`, `_deface_study`, and optional `progress` callbacks on `DicomStorage.send_study` / `RhythmStorage.upload_study`), and throttled `counters`. Pages re-fetch through the normal whitelisted endpoints on each hint, so the stream never needs its own serialization (it sits behind the same login as every other route; on a 401 reconnect `PV.live` sends the page to `/login`). `EventBus.publish()` is safe from `asyncio.to_thread` workers (`call_soon_threadsafe`); a subscriber whose queue fills is dropped and its browser reconnects with `Last-Event-ID` (replayed from the ring, else `hello.resync`). `PV.live()` in `common.js` wires it up; `PV.poll` stays as a fallback, slowed to 60 s while the stream is connected. `/studies` never overwrites a form with unsaved edits on a pushed update — it shows a "Reload" notice instead.

**First run** — With no users, `_auth_middleware` sends every page to `/setup` and APIs get 401 `setup_required`; `/login` redirects there too. The wizard routes bypass the middleware and gate themselves (see `dashboard/setup.py`). With users but no marker, an admin's browser (session, HTML) visit to `/` or `/studies` redirects to `/setup` once (Skip writes the marker).

**Authentication** — Every dashboard route except `/login`, `/health`, `/static/theme.css` and `/static/common.js` requires a user. `Dashboard._auth_middleware` resolves one from a per-user API token (`Authorization: Bearer pv_<id>_<secret>` or `X-Auth-Token`) or the `pv_session` cookie. Without one, HTML GETs redirect to `/login?next=…` and everything else gets a 401. Cookie-authenticated mutations also need `X-Requested-With: PixieVeil` (set by `PV.api`) and a same-origin `Origin` if one is sent (CSRF guard); token requests are exempt. Users are added by CLI or by an admin on `/users`; there is no self-registration. `admin` is the only permission, and it gates only user management. The old shared `http_server.auth_token` is gone (startup warns if it is set). **Attribution**: handlers call `StorageManager.record_audit()` after each study action/exam save. It appends `{at,user,action,ok,detail}` to `StudySidecar.audit` (capped at 200), stamps `exported_by` on the first successful export action, and logs `Audit: user=…`. `save_exam(actor=…)` records `manual.edited_by` in the exam sidecar. Tests get an admin + API token via `tests/test_dashboard.make_dashboard()`, and conftest points `user_store.DEFAULT_PATH` at tmp so no test touches `config/users.yaml`.

**Protocol catalog** — `config/protocols.yaml` (`storage.protocols_file`; the old `rhythm.protocol_map` key is still honoured as the path) is the single source for scanners, protocols and their RHYTHM mapping, replacing `integrations/rhythm/scanner_lookup.yaml`, `indication_lookup.yaml` and `config/rhythm_protocols.yaml` (now marked RETIRED; `open_catalog()` migrates them once when the catalog doesn't exist — keys kept so existing exams still resolve, protocols attached to the only scanner or else a wildcard "Any scanner" group, region/indication copied from an indication rule whose `protocol_name_contains` equals the protocol name). A file still in the old `rhythm_protocols.yaml` shape is read as a wildcard group. Matching (`ProtocolCatalog.match`) uses the pre-anonymization hints: scanner by case-insensitive Manufacturer+Model, then an exact (case-insensitive, whitespace-collapsed) name among that scanner's `names`, then any wildcard group's. `ExamExtractor(catalog=…)` applies it at extraction; `exam_merge.apply_catalog_match()` is the one place that writes a match into an exam (`rhythm.protocol_key`, `indication.*` with `source:"catalog"`, `scanner.catalog_id/name`, a `catalog` block, and `Protocol catalog:` notes), never touching `manual.fields` paths and clearing values a previous match set when a protocol disappears. `PUT /api/protocols` (admin; whole document + `version` → 409 if stale, 400 with `errors`) saves via `replace()` then runs `StorageManager.reapply_catalog_sync()` over every non-archived study (saves changed exams, publishes `exam`, refreshes export artifacts). `GET /api/protocols/unmatched` (`unmatched_protocols_sync`) groups unmatched studies by (manufacturer, model, protocol name) for the page's inbox. The exam's `protocol_used_hint.study_description` is recorded so re-matching works after a study's directory is purged.

**Thread safety** — Acquire `self.lock` before reading/writing `self.counters` in `StorageManager`.

## Configuration

Copy `config/settings.example.yaml` → `config/settings.yaml`. Key sections: `dicom_server`, `storage` (with `protocols_file` for the protocol catalog, optional `remote_storage.dicom`, `remote_storage.http`, and/or `remote_storage.rhythm` — the last needs `base_url` + `auth_token` + `site_code`, only works with the `rhythm` anonymization profile, and also needs each study's protocol mapped to the UUID of a `CTProtocol` registered in the RHYTHM app — done on `/protocols`), `http_server` (`users_file`, `session_idle_hours`, `session_max_days`, `secure_cookies`), `study`, `series_filter`, `defacing`, `anonymization` (profile: `research`, `gdpr`, or `rhythm`), `logging`.

## Code style

- Python 3.12+ — use built-in generics (`dict`, `list`, `tuple`) not `typing` aliases
- `logger = logging.getLogger(__name__)` at module level; no `print()`
- No bare `except:`; log at `ERROR` before re-raising
- `_underscore` prefix for private members, `UPPER_SNAKE` for module-level constants
